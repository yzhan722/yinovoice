0. 一句话结论

Stage1 已经从「本机麦克风语音闭环 Demo」推进到「可隔离部署的网页语音前台 + 租户配置 + 通话留痕 + 预约/回拨意向闭环」。
它能证明 Yino 自管配置与业务数据、Qwen Realtime 实时对话、通话结束后自动登记意向；还不能对外宣称已具备电话接入、真实挂号、真实外呼或生产级多租户。

汇报口径建议：

当前是 内部/受邀验收的 Stage1 平台切片，不是面向真实患者的生产客服。

1. 阶段定位

维度 Stage1 现状
产品目标 可复用 AI 语音客服平台；第一行业样例为口腔前台（太平洋口腔演示 Prompt）

租户模型 Demo 分区：X-Tenant-ID 头隔离；登录为前端 shell mock（demo / admin）
持久化 PostgreSQL；Stage1 独立库 yino_platform_stage1
验收环境 https://<HOST>/stage1/，进程与库与生产隔离
生产 https://8.215.80.82/ 保持回滚基线，本阶段不覆盖

Stage1 要回答的问题是：平台核心能否独立跑通「听—说—记—转意向」，而不是「能否替代诊所现有挂号系统和电话总机」。

2. 系统构成

浏览器（Vue 3 控制台）
    │  实时音视频 + 配置/记录 API
    ▼
LiveKit（房间与媒体）
    │  named-agent 调度 + 短期 token
    ▼
Runtime voice-agent
    │  Qwen Audio Realtime（默认）
    ▼
Platform API（Control Plane）
    │  实例 / 通话 / 预约 / 回拨
    ▼
PostgreSQL（租户隔离表）
组件 路径 职责
控制台前端 apps/control-plane/web 租户工作台、实例、实时语音、通话、预约、回拨、知识库配置
Platform API apps/control-plane/api 配置、LiveKit token、通话记录、录音元数据、预约/回拨 CRUD、意向抽取
Voice Agent apps/runtime/voice-agent Qwen Realtime 双向音频；打断（barge-in）；按实例配置合成 Prompt
数据库 Docker Postgres，Stage1 独立库 实例、通话、消息、预约、回拨；重启不丢

默认实时链路：

浏览器麦克风 → LiveKit → Qwen Audio Realtime → 立即回放 → 浏览器扬声器
  • 模型默认：qwen-audio-3.0-realtime-plus
  • 音色默认：longanqian（实例可改）
  • 话轮：smart_turn；用户 partial/final 转写；客服增量文本 + 音频
  • 首包音频在 response.audio.delta 即播，不等 response.done
  • 用户插话会打断当前回复，并隔离迟到的旧音频/文本

可选回退：Fun-ASR + LLM + TTS pipeline（非默认、不作为 Stage1 主验收）。

5. 明确不在 Stage1 范围

汇报时建议主动列出，防止听众按「完整电话客服」理解：

  • 真实 SIP / 运营商号码 / 主动外呼 / 诊后回访营销电话
  • 面向真实患者的公开生产服务
  • 生产级身份认证、RBAC、套餐计费、发票
  • Google Calendar / 诊所管理系统正式连接器
  • 医生排班、项目时长、档期冲突引擎
  • 配置发布：版本 Diff / 回读 / 回滚产品化（原则已定，产品未做完）
  • 录音转自有 S3；跨区域复制；完整 SLA
  • 模板市场、第三方模板交易
  • 完整 Vapi Adapter（Vapi 不在当前主链路）
  • AI 医疗诊断或个性化治疗决策
  • 开场强制声明 AI 身份或法定录音告知（Demo 未按生产合规验收）

6. 建议演示剧本（5–8 分钟）

适合汇报现场，一条主线即可：

  1. 登录租户（demo）→「我的实例」：展示已有实例或新建一条非空演示实例。
  2. 知识库/配置：改一句业务 Prompt 或切换音色并保存。
  3. 实时语音：进房，完成至少 3 轮（问候 → 问地址/项目 → 「想约周五洁牙」）。
  4. 打断：客服说话时插话，确认旧音频不回放。
  5. 结束通话 →「通话记录」：有转写，必要时可播放浏览器录音。
  6. 预约结果：出现「语音自动」意向（缺电话会标待确认）。
  7. 回拨任务（可选）：若只说「请回电」则进任务队列，强调不会真拨出去。
  8. 边界说明：问价格/确诊时，模型应拒绝编造并引导到店/人工。

运营视角：用 admin 打开「通话记录」，证明同一 Demo Tenant 记录可见。
不要在汇报材料中粘贴完整对话、患者信息和任何 API Key。
